# セルフレビュー

目的は**後から直す手戻りを減らすこと**。指摘を増やすことではなく、**あとで確実に踏む穴を潰すこと**を狙う。

## 差分を集める（3 つとも）

レビュー対象は**このブランチが `develop` に入れようとしている変更全体**。直前のコミットだけを見るとブランチ全体を取りこぼす。

```bash
git diff --no-renames develop...HEAD      # このブランチが入れたコミット済みの変更
git diff --no-renames HEAD                # 未コミットの変更（ステージ済み含む）
git ls-files --others --exclude-standard  # 未追跡の新規ファイル
```

- **`...`（3 点）を使う。** `develop..HEAD`（2 点）にすると、`develop` 側が進んでいるときに相手側の変更まで差分に出て、自分が書いていないコードをレビューすることになる。3 点なら**分岐点からこのブランチが入れた変更だけ**。
- **未追跡の新規ファイルは `git diff` に出ない。** 3 つ目を必ず実行する。
- **`--no-renames` を省かない**（移動元のパスが落ちる）。
- **1 本のパイプにまとめない**（どれかが失敗しても全体は成功し、「変更なし」に見えたまま見落とす）。
- **`git status --porcelain` は使わない**（リネームが `R old -> new` の 1 行になりパスとして取り出せない）。

## 観点（この順。当てはまらないものは飛ばす）

### 1. プロダクト方針（最優先）

[CLAUDE.md の「最重要方針」](../../../CLAUDE.md)を弱める変更になっていないか。

- **誤出品を起こさないか。**
  - 編集ページの自動クリックが、Background への `CHECK_AUTO_TAB` 確認を通らずに走る経路ができていないか（手動で開いた編集ページで動いたら事故）。
  - 一括処理の**対象の絞り込み条件と件数**が変わっていないか。ユーザーが選んでいない商品が `QueueItem[]` に入りうるか。
  - 失敗時に編集タブを閉じる変更になっていないか（`handleEditFailed` はタブを残す）。
  - 商品間の待機（`WAIT_BETWEEN_ITEMS_MS` + `WAIT_RANDOM_MS`）を縮めていないか。
- **ラクマ側の DOM 変更に耐えるか。**
  - 一覧ページの新しいセレクタを `src/content/list/infra/constants.ts` の外に直書きしていないか。
  - 編集ページのボタンを `css-*` クラスで掴んでいないか（ハッシュなのでビルドごとに変わる。テキスト一致で探す）。
  - **要素が見つからないときに黙って続行していないか**（見つからない＝ラクマ側が変わった可能性なので、安全に止まって知らせる側に倒す）。`waitForButton` の reject を握り潰していないか。

### 2. 壊れても気づけないもの

- **不可逆操作のガード**: 一括クリック・一括出品の**件数と条件**。ループが途中で失敗したとき**部分適用で終わっていないか**（何件目まで処理したかが `currentIndex` / `failed` で分かるか）。
- **失敗しても止めない処理は、失敗が観測できないと不具合と区別できない。** `catch` で握り潰していないか、`src/common/logger.ts` の `warn` が出るか。`notifyProgress` の `.catch(() => {})` のように**意図的に握り潰す箇所は、その理由がコメントで読めるか**。
- **Background の状態が取り残されないか。** `activeEditTabId` / `waitingForNewTab` / `running` が、例外経路・タブが閉じられた経路も含めて必ず戻るか。`chrome.alarms` を張ったまま終わっていないか（`stop()` は `clear` している）。
- 設定値（セレクタ・待ち時間・ID）をコードに直書きしていないか。`src/content/list/infra/constants.ts` に置くべきものではないか。
- スタブのテストでは検出できない箇所（このリポジトリには自動テストが無いので、**すべてがこれに当たる**。実際に Chrome に読み込んで確認したかどうかを自分に問う）。

### 3. 実行時に落ちるもの

- 検証なしの型アサーション（`as HTMLElement` など）。DOM から取った要素は `null` になりうる。
- `null` / `undefined` へのアクセス。`querySelector` の戻り値をそのまま使っていないか。
- **`await` 忘れ**。非同期の出品処理を待たずに次へ進むと、順序が崩れて誤出品につながる。`void` を付けて意図的に待たない箇所は、待たなくてよい理由が読めるか。
- 握り潰した `catch`。
- 後始末されない fire-and-forget（`window.setTimeout` のポーリング、イベントリスナー、`chrome.alarms`）。
- **Service Worker が破棄されると消える状態に依存していないか**（キューは SW のメモリ上にのみある）。
- 外部入力（DOM のテキスト、`chrome.runtime.sendMessage` の応答）の未検証。`CheckAutoTabResponse` を `undefined` になりうる前提で扱っているか。
- secret がログや応答に出ていないか。

### 4. 出す前の形式

- **型チェック・ビルド・lint を実際に通したか**（`npx tsc --noEmit` / `npm run build` / `npm run lint`）。通していないなら通す。**この 3 つは通るのが正常。**
- `npm run format:check` で自分が触ったファイルが増えていないか（既存 16 ファイルの失敗は対象外）。
- 一時設定・デバッグ出力・コメントアウトした旧コードが残っていないか。
- 依頼されていない変更が混ざっていないか（既存コードの format 一括修正を含む）。

## 出し方

- **Must / Should / Nit の 3 段階で最大 5 件**（件数が多いと読まれない）。
  - **Must** = 直さないと先に進めない（壊れている・方針に反する・データを失う）
  - **Should** = 直したほうがよい（いま直さないなら理由が要る）
  - **Nit** = 好みの範囲
- 各指摘は「**どこが・なぜ問題か・どうなると壊れるか**」を 1〜2 行。修正方法の長い説明は要らない。
- **点数を付けない**（較正点が無く再現性がない。平均が重い問題を薄める）。総合評価は Must / Should の件数で書き、合否は「**Must が 0 件か**」で判断する。
- **5 件を埋めようとしない。** 無ければ「Must / Should なし」で終える。

## 指摘しないこと（見つけても書かない。読む量が増えるだけ）

- コードスタイル・フォーマット（ESLint / Prettier の領分）
- 変数名・コメントの有無
- 動作に影響しないリファクタ提案（DRY 化など）
- カバレッジの低さそのもの（**押さえていない挙動を具体的に言えるなら書く**）
- 好みや慣習の違い

## 推測で指摘しない

呼び出し元・呼び出し先まで実際に読んでから書く。**「たぶん壊れる」は書かない。** どう壊れるかを 1 行で言えないなら、指摘ではなく**確認事項**として分ける。
