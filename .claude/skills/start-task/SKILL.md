# タスクに着手する

規約の正本は [CLAUDE.md](../../../CLAUDE.md)。ここには**手順**だけを書く。

## 1. 対象パッケージを確定する

- **どちらの拡張のタスクかを最初に決める**（`packages/mercari` / `packages/rakuma` / 共有部品の `packages/core`）。依頼文に無ければ聞く。推測で片方に決めない。
- **2 つの拡張は中身が別物**（CLAUDE.md の「2 つの拡張は中身が別物」）。片方で直した不具合がもう片方にもあるとは限らないし、あっても別のコードを別のやり方で直すことになる。**両方に同じ趣旨の変更を頼まれたら、パッケージごとに別タスク・別コミットとして扱う。**

## 2. 読む（推測で書き始めない）

- **対象パッケージの CLAUDE.md の「着手前に読むもの」索引にある一次資料と、該当コードを直接読む。** 索引に無い領域なら、該当ディレクトリのコードを読んでから始める。
- **文書とコードが食い違ったらコードが正。** 既知のズレは各パッケージの CLAUDE.md にまとめてある。古い記述を見つけたらその場で直し、**一覧に足して放置しない**。
- **索引は `develop` 時点の構成を指している。** 未統合の作業ブランチの上にいると構成が違うことがあるので、**どのブランチの上で作業しているかを確認してから**ファイルを開く。
- **過去のメモや会話に書かれた構成図を信用しない。** 廃止された仕組みがそのまま残っていることがある（元リポジトリでは実際に、削除済みのディレクトリやファイルがドキュメントと会話の中で生き延びていた）。**必ず現物のファイルで確かめる。**
- **確かめていないことを断定しない。** サイト側の DOM・Chrome 拡張 API の制約は、実際に動かすか公式ドキュメントで確認するまで「要検証」と明記する。「たぶん動く」で設計を進めない。

## 3. スコープを決める

- **依頼されたスコープを勝手に広げない。** 作業中に見つけた別の問題は、直さずに書き出して報告する。**1 コミットは 1 つの目的に絞る。**
  - **既存コードの一括整形を混ぜない。** メルカリ側の `format:check` は元から落ちている。ついでに直さない（差分が膨れて本来の変更が埋もれる）。
  - **もう片方のパッケージへの「ついで」の変更を混ぜない。**
- **方針決めと実装を 1 つの作業単位に混ぜない。** 方針が定まっていないものは、**決めて書き残すまでを 1 単位**にし、実装は別にする。決まっていない状態で書いた実装は、方針が動いたときにまるごと捨てることになる。
- **方針を変える判断をしたら理由を残す。** 選ばなかった案とその理由まで書く。

## 4. ブランチを切る

`develop` が統合ブランチ。**`develop` と `main` で直接作業しない。**

```bash
git switch develop && git pull --ff-only   # origin が無い間は pull を飛ばす
git switch -c <feature|fix|docs|refactor>/<英小文字の短い説明>
```

`git pull --ff-only` が失敗したら `develop` が分岐している。**勝手にマージせず、報告して指示を仰ぐ。**

命名規約は [CLAUDE.md](../../../CLAUDE.md) の「ブランチ運用の補足」にある（`feature/` を既定にせず、中身で選ぶ）。ブランチ名にパッケージ名を入れてもよい（例: `fix/rakuma-read-price-from-offers`）。

**worktree で作業しているときは、そのブランチは既に切られている。** 新しく切らず、名前が規約どおりか確認する。自動命名（`claude/...`、`worktree-...`）のままなら直す:

```bash
git branch --show-current
git branch -m <規約名>
```

## 5. 実装する

CLAUDE.md の「最重要方針」と、対象パッケージの CLAUDE.md の「最重要方針」に照らしながら書く。とくに:

- 一括出品・一括再出品・一括削除・説明文の置換は**取り消せない実操作**。対象の絞り込み条件と件数のガードを先に決める。
- セレクタとページ判定は**サイト側の変更で壊れる**。新しいセレクタは対象パッケージの定数ファイルに置き、要素が見つからないときに黙って続行しないこと。
- **パッケージをまたいで import しない。** 共有するなら `packages/core` に置き、文字列やキー名は呼び出し側から注入する。

## 6. 既定の停止点はコミット

1. **品質チェックを通す** → `quality-check` スキル（ルートで両パッケージ分）
2. **セルフレビューする** → `self-review` スキル
3. **コミットする** → `commit` スキル
4. **やったことを数行で報告して終える**

コミットまでで止める。**マージまで自動で進めない。** 統合するかどうかは人が判断する。「マージして」と言われたときだけ `merge` スキルに進む。作業ブランチの push もしない（ローカル限りの運用）。

**逆方向の指示を尊重する。** 「コミットしないで」「品質チェックだけ」「調べるだけ」と言われたら、そこで止めて残りをやらない。
