# 対応済みセッション・ブランチ・worktree の整理

規約の正本は [CLAUDE.md](../../../CLAUDE.md) の「ブランチ運用の補足」。このスキルは**溜まったものをまとめて掃除する**手順。マージ直後に 1 本だけ片付けるときは [merge スキル](../merge/SKILL.md) の「後始末」を使う。

**洗い出しと実行を分ける。** 対象を表にして報告し、**人が判断してから**消す。頼まれていないのに消し始めない。

## 1. 現状を集める

```bash
git worktree list          # worktree とそれが持つブランチ
git branch -vv             # ローカルブランチ（+ 印が worktree に占有されているもの）
git branch --no-merged develop
git log --oneline origin/develop..develop   # develop の未 push 分
```

セッション側は `mcp__ccd_session_mgmt__list_sessions` で一覧を取り、**`cwd` がこのリポジトリ配下のものだけに絞る**（他プロジェクトのセッションが混ざる）。

各 worktree の未コミット変更も見る:

```bash
git -C <worktree の絶対パス> status --short
```

- **worktree 内から相対パスで `git -C` を打たない。** 解決に失敗する。絶対パスを使う。

## 2. 対象かどうかを判定する

**次の 3 つを全部満たすものだけが対象。**

1. **`develop` より先行しているコミットが 0 本** — `git rev-list --count develop..<ブランチ>` が `0`
2. **worktree の作業ツリーがクリーン** — `git status --short` が空
3. **セッションが実行中でない** — `list_sessions` の `isRunning` が `false`

加えて次は**対象外**:

- **このセッション自身とその worktree** — 最後に回す（ユーザーの指示を受けてから）
- **`main` と `develop`** — origin と共有する 2 本。消さない（先行コミットが残っていても push は人が判断する）
- **コミットが残っていて未マージのブランチ** — `git branch --no-merged develop` に出るもの

### 見落としやすいもの

- **worktree を持たない孤児ブランチ。** 自動命名（`claude/...`）を規約名にリネームしたとき、`git worktree list` に出ない古い名前のブランチが残ることがある。`git branch -vv` で `+` が付かない行を見る。
- **セッションの `branch` フィールドは古いことがある。** リネーム後も作成時の名前が記録されたままなので、**実際のブランチは `git worktree list` で確認する**（セッションの記録を信用しない）。

## 3. 表にして報告し、判断を仰ぐ

セッション・ブランチ・worktree の 3 つを、**それぞれ「消す / 残す」と理由**を添えて出す。「全部マージ済み」で済ませず、残すものにも理由を書く。

**`develop` が origin より先行しているなら、そのコミット数も報告する。** 掃除自体は安全（コミットは `develop` に残る）だが、push の判断は人がする。

## 4. アーカイブ → worktree → ブランチ の順に片付ける

**この順番を崩さない。** 逆順だとセッションが生きている worktree を消すことになる。

### 4-1. セッションをアーカイブする

`mcp__ccd_session_mgmt__archive_session` を使う。**アーカイブは可逆**（`unarchive_session` で戻せる）。

- **`delete_session` は使わない。** 転写もブランチも消えて戻せない。ユーザーが明示的に「削除」と言った場合だけ。
- ユーザーが個別に「これは残す」と言ったら**そのセッションの worktree とブランチも残す**（3 点セットで扱う）。

### 4-2. worktree を消す

**アーカイブしても worktree のディレクトリは消えない。** HEAD が detached になるだけで、ディレクトリもブランチも残る（実測）。明示的に消す:

```bash
git -C <worktree の絶対パス> status --short   # 空であることを再確認してから
git worktree remove <worktree の絶対パス>
```

**`--force` を使う前に、失うものが無いか必ず見る**（詳細は [local-setup スキル](../local-setup/SKILL.md) の「worktree とブランチの関係」）。

### 4-3. ブランチを消す

```bash
git branch -d <ブランチ>
```

- **`-D` は使わない。** `-d` が拒否するのは「まだマージされていない」というサイン。拒否されたら止まって確認する。
- 作業ブランチは origin に push しない運用なので、リモート側の削除は不要。

## 5. 片付け後にもう一度状態を出す

`git worktree list` と `git branch -vv` を取り直して、**残ったものを表で報告する**。

**他のセッションが並行して動いていると、作業中に `develop` が進む。** 判定に使ったハッシュと最終状態がずれるので、**最後の状態は取り直した値で報告する**（古い値を使い回さない）。

## やらないこと

- **洗い出しの流れで勝手に消さない。** 報告と実行の間に人の判断を挟む。
- **`delete_session` を既定にしない。** 既定はアーカイブ。
- **実行中セッションの worktree に触らない。** 未コミットの変更ごと消える。
- **`main` / `develop` を消さない・勝手に push しない。**

## 報告に入れるもの

- アーカイブしたセッション（と、指示で残したもの）
- 削除した worktree と、削除前に作業ツリーがクリーンだったこと
- 削除したブランチと、`-d` で消えたこと（＝マージ済みの確認が取れたこと）
- 片付け後の worktree / ブランチ一覧
- `develop` の未 push コミット数など、人の判断が要る残作業
