# Rakuma Bulk Lister

ラクマ（fril.jp）の出品作業を一括化する Chrome 拡張機能。

- **一括下書き保存**: 「出品した商品」（`/sell`）で商品を選択し、フリマアシストの再出品ボタンを順にクリックして、複製された内容を**下書きとして保存**する
- **下書き一括出品**: 「下書きの商品」（`/draft`）で下書きを選択し、順に出品する
- **一括削除**: `/sell`・`/draft` のどちらでも、選択した商品を順に削除する
- **説明文の一括置換**: `/sell` で確定版と原本の JSON を読み込み、出品中の商品の**説明欄だけ**を
  順に確定版へ置き換えて保存する（詳細は「説明文の一括置換」）

再出品はこの2段構えで行う。`/sell` で下書きに溜めてから、内容を確認して `/draft` で公開する。
`/sell` 側の操作では出品は発生しない。

## 前提

- 一括再出品には Chrome 拡張機能「フリマアシスト」のインストールが必要（`/sell` に注入される `#clone-item` ボタンを利用するため）
- 下書き一括出品はフリマアシスト不要

## 仕組み

```
① 一覧ページ (content-list.js)
   /sell:  チェックボックスで選択 → フリマアシストの再出品ボタンをクリック
   /draft: チェックボックスで選択 → Background が編集ページをタブで開く

   削除: チェックボックスで選択 → 削除リンクをクリック（ページ遷移が起きる）

② Background (background.js)
   処理キューの管理・タブの追跡・完了の検知・商品間の待機時間制御

③ 出品フォーム (content-form.js)
   Background に自動処理対象タブか確認したうえで、モード別にボタンを押す
   relist  /item/new           （フリマアシストが開く）→「下書きに保存する」
   publish /drafts/{hash}/edit （Background が開く）  →「確認する」→「出品する」
   replace /item/{hash}/edit   （Background が開く）  → 説明欄を書き換え →「確認する」→「更新する」
```

### 出品完了の判定は Background 側で行う

出品フォームのタブを `chrome.tabs.onUpdated` で監視し、**ボタンを押したあとに
出品フォームの URL から離れたこと**をもって完了とみなす。

Content Script 側で遷移を監視しない理由は、遷移先が別オリジン（`item.fril.jp`）に
なりうるため。その場合 Content Script は遷移前に破棄され、完了を見届けられない。

Background が離脱を見始めるのは `FORM_SUBMITTED` を受け取ってからなので、
Content Script は**ボタンを押す前に**これを送る（押した直後だと、遷移で
破棄されて送れないことがある）。**送れたことを確認できなければ押さない。**
押したのに Background が知らないままだと、遷移しても完了とみなされず、
ウォッチドッグが時間切れになるまで「自動操作が始まりませんでした」としか
分からない。送れなかった場合は通信失敗を理由に失敗として扱う。

### 入力が終わるまで待ってから保存する

フリマアシストの流し込みはテキストが速く、**画像だけ遅い**
（`img.fril.jp/tmp_img/` へアップロードされるまで時間がかかる）。
「何か値が入ったか」で判断すると早すぎて、画像が欠けた下書きができる。

待ち方は、再出品元の内容が分かっているかで変える。

- **分かっている場合**: 各項目のスナップショット（商品名・価格・説明・各 `select`・
  画像枚数）が**元と一致するまで**待つ。
- **分からない場合**: スナップショットが**5秒間まったく変化しなくなるまで**待つ。

どちらも0.5秒ごとに確認し、最大2分待つ。

「変化が止まったか」だけで判断してはいけない。画像は1枚ずつ間隔を空けて
アップロードされるため、アップロードの合間が安定時間を超えると、
**画像が足りないまま完了と誤判定**して欠けた下書きができてしまう。

カテゴリや配送方法はボタンのラベルとして出るが、手数料の案内など内容が
変わりうるボタンも混ざるため、安定判定には含めない。

### 再出品元との差分チェック

保存の直前に、再出品元の商品ページ (`https://item.fril.jp/{hash}`) の内容と
突き合わせる。**足りていない場合は保存せず、差分を失敗理由として残す。**

検出したいのは**内容の欠落**なので、比較には向きを持たせる。フォーム側が元より
多い・書式が違うぶんは問題にしない。JSON-LD とフォームは別々のシリアライズ経路で、
同じ内容でも数文字ずれることが実際にある（実測: 元779文字に対しフォーム782文字）。
厳密一致を求めると、内容は揃っているのに永久に保存できなくなる。

| 項目 | 判定 |
| --- | --- |
| 商品名 | 空白を落とした状態で不一致なら失敗 |
| 商品説明 | フォーム側が5文字以上**短ければ**失敗（長いぶんは可） |
| 価格 | 数値として不一致なら失敗 |
| 画像枚数 | フォーム側が**少なければ**失敗（多いぶんは可） |

商品ページはサーバーレンダリングされており、JSON-LD (Product) から
商品名・説明・価格・ブランドが取れる。画像は JSON-LD に1枚しか無いため、
og:image と同じ商品番号を持つ大サイズ (`/l/`) の画像URLを重複を除いて数える。

実機で、JSON-LD とフォームの値は商品名・説明とも完全一致することを確認済み
（ハッシュ一致）。そのため文字列は厳密に比較する。

取得は Background で行う（`item.fril.jp` は別オリジンのため host_permissions が必要）。
Service Worker には DOMParser が無いので正規表現で抜き出す。
JSON-LD は1ページに複数置かれうるので、**全ブロックを走査して `@type` が Product の
ものを選ぶ**（ルートが配列のときと `@graph` の下にあるときも見る）。先頭のブロックを
決め打ちすると、ラクマ側が Product より前に別の JSON-LD を足した瞬間に全項目が null になり、
差分チェックが黙って省略される。Product が見つからないときは warn を出す。
取得に失敗した場合は差分チェックを省略し、入力が落ち着いたかどうかだけで判断する。

### 一括削除はページ遷移をまたいで進む

ラクマの削除は `jquery_ujs` のリンク（`data-method="delete"`）で、`data-remote` を
持たないため**クリックするとページ遷移が起きる**。1件削除するたびに一覧が
再読み込みされ、Content Script も作り直される。そのため削除もキューで駆動する。

```
Background → CLICK_DELETE → 一覧で削除リンクをクリック → ページ遷移
  → 一覧が再描画 → Content Script が LIST_READY（表示中の商品ID）を送る
  → Background が対象IDの消滅を確認 → 成功として次へ
```

#### 削除すると1ページ目に戻る

削除後の再読み込みで一覧は**1ページ目に戻る**。そのため2ページ目以降の商品を続けて
削除しようとすると、対象がDOM上に無くて失敗する。

対策として、**開始時のページ番号を覚えておき、削除のたびにそのページへ戻してから**
対象を探す。次の2つが成り立つので、そのページに戻れば必ず見つかる。

- **対象は必ず1ページに収まる**。`syncItems` がDOM変化のたびに
  `SelectionManager.retain()` を呼ぶため、ページを送った時点で前ページの選択は
  破棄される。つまり開始時の選択は現在ページのものだけになる。
- **同じページの商品を削除しても、そのページの残りは逃げない**。削除すると後続が
  1つずつ前に詰まるが、ページP内の商品はP内に留まり、P+1以降の商品がPへ
  繰り上がってくるだけ。Pより前の商品は動かない。

ページ送りはURLを変えずAJAXで一覧を差し替えるので、`.pagination .page.current` の
表示が目的のページ番号に変わるまで待つ。「最後のページ」へのリンクはラベルが記号で
番号を持たないため、リンクの解決はテキストと `href` の両方で行う。これにより
1ページ目から5ページ目へも1回の移動で到達できる。「…」で省略されていて直接の
リンクが無い場合は、目的地に近づく方向へ段階的に移動する。

想定が崩れて目的のページに見つからなかった場合の保険として、全ページを順に探す。

#### 成否の判定

「表示中の一覧に対象が残っていないこと」は削除の証拠にならない。1ページ目に戻るので、
別ページにいるだけかもしれないため。

- 件数が読めるページ（`/sell`）: **総件数が減ったか**で判定する。
  情報行（`122件中 31 - 60件`）はタブごとに存在するので、表示中のものだけを使う。
- 件数が読めないページ（`/draft` はページャが無く全件表示）:
  対象IDが一覧に残っていないかで判定する。

押した結果を確認してから次へ進むので、削除できていないのに進み続けることがない。

商品間の待機は Content Script 側で 2〜4 秒入れる。`chrome.alarms` は短い遅延を
指定できず、また削除はページ遷移そのものが間隔になるため、他モードのような
60〜75 秒の待機は挟まない。

### 削除の確認ダイアログの扱い

削除リンクには `data-confirm="本当に削除してもよろしいですか？"` が付いており、
`jquery_ujs` がネイティブの `confirm()` を出す。これは Content Script 側から
応答できず処理が止まるため、**クリックの直前だけ `data-confirm` を外し、直後に必ず戻す**。

そのぶん、一括削除の開始前に拡張側で必ず確認を取る（件数と取り消せない旨を表示）。
手動でクリックしたときの確認ダイアログはそのまま残る。

削除リンクは `data-method="delete"` で特定したうえで、**ラベルが「削除」であることも
確認**してからクリックする。取り消せない操作なので、どちらか一方でも合わなければ
クリックせず失敗として記録する。

### Service Worker の破棄に耐える

MV3 の Service Worker はアイドル状態が続くと破棄される。本拡張は商品間に 60〜75 秒の待機を
挟むため、待機中の破棄は**必ず起きる**。そのためキューの状態は変更のたびに
`chrome.storage.session` へ書き戻し、すべてのイベントハンドラの先頭で復元してから処理する。

タイマー類も `setTimeout` ではなく `chrome.alarms` を使う（`setTimeout` は Service Worker の
破棄とともに消えるため）。

- `next-item` アラーム: 次の商品の処理開始
- `watchdog` アラーム: 1 商品の処理が 5 分以内に完了しない場合に打ち切る（`ITEM_WATCHDOG_MS`）

### 一覧の描画をMutationObserverで待つ

商品リストはサーバーHTMLに含まれず、クライアント側で描画される。さらにページ送りは
URLを変えずにAJAXで一覧を差し替えるため、Content Script は再実行されない。
そのため `MutationObserver` で `body` 配下の変化を監視し、商品が現れるたびに
チェックボックスを付け直す（付与済みの商品はスキップするので何度呼んでも安全）。

一覧から消えた商品の選択は破棄する。ページ送りで表示外になった商品を選択したまま
開始してしまうのを防ぐため。

### その他の設計上の判断

- 出品フォームのボタンは Chakra UI のハッシュクラスのため**テキストで特定**する
- 手動で開いた出品ページでは何もしない（Background への確認で判別）
- ボタンを押す前にフォームへ値が入るのを待つ（フリマアシストの入力完了前に
  空のフォームを保存・送信しないため）
- 押すボタンはページのボタン名ではなくモードで決める。`/item/new` と
  `/drafts/{hash}/edit` はどちらも「下書きに保存する」と「確認する」を持つため
- 失敗時（バリデーションエラー・タイムアウト等）はタブを残してユーザーが確認できるようにする
- 一覧ページを再読込しても、実行中のキューの進捗は Background から取得して復元される
- 一括下書き保存・一括出品も、削除と同じく開始前に確認ダイアログを出す（件数・待機・所要時間の目安・処理順）。
  出品は取り消せず、どちらも 1 件あたり 1 分以上かかるため。待機の表示値（`CONFIG.ITEM_WAIT_*`）は
  Background の `WAIT_BETWEEN_ITEMS_MS` / `WAIT_RANDOM_MS` と手でそろえている

### 注入 UI の見た目

- **ラクマ本体はダークモードに対応していない**（2026-10-02 実測: `prefers-color-scheme` の
  ルールが無く、OS がダークでも背景は白のまま）。そのため、浮遊する UI（下部のドック・パネル・
  トースト・確認ダイアログ）だけが配色の設定（`auto` = OS に従う / `light` / `dark`。
  `chrome.storage.local` の `rbl-theme`）に従い、商品行に差し込む部品（チェックボックス・選択順）は
  白い背景に合わせて常にライトの値で描く
- 色の値は `src/common/theme.ts` のトークンだけに置き、注入 UI と popup の両方がそこから CSS を組み立てる
- ラクマの赤 `#ec0606` は白文字とのコントラスト比が 4.57 で AA ぎりぎりのため、文字を載せる塗りには
  一段濃い `#d40a0a`（5.46）を使い、元の赤は装飾（線・グラデーション）にだけ使う
- 確認ダイアログは `<dialog>` + `showModal()`。初期フォーカスはキャンセル、Esc・背景のクリックも中止。
  答えはボタンのクリックで直接確定させる（`close` イベントは描画の都合で遅れて届くことがあるため）。
  `<dialog>` を出せないときは `window.confirm` に切り替え、確認そのものは省かない
- 行の部品はラクマ側の要素を動かさず、`div.deal-item` の先頭に `label` を 1 つ差し込むだけにする。
  Shift を押しながら選ぶと、直前に押した行からの範囲をまとめて選べる（選択順は表示順）
- ドックは画面下に固定されるので、ページ末尾（ページャ）を覆わないよう body の末尾に同じ高さの余白を足す。
  トースト・パネルはドックの高さ（処理中は 2 段に伸びる）を `ResizeObserver` で追い、常にその上に置く
- popup（ツールバーのアイコン）は、処理の状況（Background の進捗を 1.5 秒ごとに取得）・各一覧ページへの導線・
  配色の切り替えを出す。配色は描画前に当てたいので、`chrome.storage.local` に加えて popup の `localStorage` にも控える

### 説明文の一括置換

出品中の商品の説明文を、あらかじめ用意した確定版の本文へ 1 件ずつ置き換えて保存する。
表記の統一など、多数の商品の説明欄だけを機械的に直したいときに使う。
（同じ目的の機能が mercari-draft-publisher にもあり、手順と安全装置はそちらと揃えてある。
ラクマの DOM は別物なので作りは別。）

```
/sell の一括操作バー「説明文の一括置換」 → パネルを開くだけ（保存には向かわない）
  ├── 確定版 JSON と原本 JSON（どちらも [{ id, name, desc }]。id はラクマの商品ID）を検証して読む
  ├── 処理対象 / 記録上の適用済み / 対象外（原本なし・1000字超・CR混入）に振り分ける
  ├── 件数・待機秒数・処理順を出して確認ダイアログ。ここが唯一の人の止め時
  └── START_QUEUE (mode=replace) → Background が /item/{hash}/edit をタブで開く
        └── content-form (replace.ts)
              ├── 商品名をデータと照合（違えばスキップ）
              ├── 説明欄の現在値を読み、確定版なら「適用済み」、原本と違えばスキップ
              ├── プロトタイプの value setter + input/change で確定版を書き込み、読み直して照合
              ├── 商品名が変わっていないことを確認
              ├── 「確認する」→「更新する」をテキスト完全一致で探してクリック
              └── /sell?is_new=0 へ遷移 → Background が item.fril.jp の JSON-LD で本文を再照合
```

**確定版の JSON だけでは動かない。** 開いた時点の説明欄が**原本**と一致することを確認してから
書き換える。取得後に人が直した商品を、古い原本から作った確定版で上書きしないため。
一致しない商品はスキップとして記録し、あとから確認できるようにする。

**保存に向かう前に 4 段の照合を通す。** 商品名の一致（取り違え防止）、現在値と原本の一致、
書き込み後の値と確定版の一致（React の状態に反映されたか）、書き込み後も商品名が
変わっていないこと（説明欄以外に触っていないか）。どれか 1 つでも通らなければ保存しない。
照合は文字数と FNV-1a（32bit）ハッシュの両方で行う（`src/common/text-fingerprint.ts`）。

**押すのは「確認する」→「更新する」だけ。** 編集ページにも「下書きに保存する」があるが、
これを押すと出品中の商品が下書きへ落ちる可能性があるため触れない。「出品する」「削除」も押さない。
確定ボタンはテキスト完全一致で探し、見つからなければ押さずに止める。

**保存後は商品ページで再照合する。** 「更新する」を押すと `/sell?is_new=0` へ遷移する
（Background の URL 監視で完了を検知）。Background が `item.fril.jp/{hash}` の JSON-LD から本文を
読み直し（反映の遅れを見て 3 回まで）、改行を LF に揃えたうえで確定版と一致して初めて
`applied` とする。一致しない・読めないときは `unverified`（保存自体は済んでいる可能性がある）。

この再照合は fetch を伴い数秒かかる。`tabs.onUpdated` は 1 回の遷移で複数回（`url` / `status`）届くため、
照合を await している間に完了処理が再入すると**同じ商品を二重に完了させ、次の商品を飛ばす**
（2026-09-28 の実機検証で実際に起きた: 2 件目の記録に 1 件目の照合結果が書かれ、2 件目は開かれなかった）。
そのため await の前にフェーズを `verifying` に変えて、`submitting` のときだけ完了処理に入る。

**結果は 5 種類。** 成功（applied）/ 適用済み（already）/ スキップ（skipped）/ 失敗（failed）/
未確認（unverified）。商品IDごとの最新結果を `chrome.storage.local` に持ち（`src/common/replace-store.ts`）、
次の実行では成功と適用済みを対象から外す。**ただし記録の確定版と今回の確定版が同じ本文のときだけ**
（文字数とハッシュで比べる）。さらに記録の内部で辻褄が合っていること（`applied` なら保存後の本文が
確定版と一致、`already` なら開いた時点の本文が確定版と一致）も確かめる。合っていない記録は
信用せず、その商品は再び処理対象にする。確定版を改訂して 2 回目を流すときに、商品IDだけで除外すると
改訂分が 1 件も適用されないため。**記録が無くても二重に保存されることはない**——開いた時点の
本文が確定版なら「適用済み」、原本でも確定版でもなければスキップになる。
パネルの「結果を出力」で記録を JSON としてダウンロードできる。

**説明欄や確定ボタンが見つからないときは残りを開かずに止める。** その商品固有の事情ではなく
ラクマ側の変更を疑うべき状況なので、1 件ずつ失敗を積み上げない（`FORM_FAILED` の `fatal`）。
編集ページが開けない・照合が通らないといった商品固有の失敗は記録して次へ進む。

商品間の待機は画面で指定した基準秒数（既定 `REPLACE_WAIT_BASE_MS` = 60 秒、下限 30 秒）に
0〜15 秒のランダム分を足す。下限が 30 秒なのは `chrome.alarms` がそれ未満を扱えないため。
「停止」は次の商品を開く前に効く。処理中の 1 件は、「更新する」を押す前なら
Background への再確認（`CHECK_AUTO_TAB`）で気づいて保存せずに打ち切り、押したあとは照合まで終える。

### 実機で確認済みの動作（2026-09-20 時点）

**publish モード（`/draft` の一括出品）は通しで動く。** 下書き1件を選んで実行し、
次を確認した。

| 確認点 | 結果 |
| --- | --- |
| 出品の実行 | 選んだ下書きが実際に出品された。`/draft` から消え、`/sell`（出品した商品）に現れる |
| 完了の検知 | 実行から20秒以内に「完了 1/1」。失敗0件でウォッチドッグにも到達しない |
| 「出品する」押下後の遷移 | **URLが変わる。** Background の URL 監視による完了判定がそのまま機能する |

懸念していた「出品完了でURLが変わらず、実際には出品されているのにウォッチドッグで
失敗扱いになる」ケースには該当しなかった。Content Script 側からの完了通知を足す必要はない。

**relist モード（`/sell` の一括下書き保存）も通しで動く。** 1件の実行と3件の実行で
次を確認した。

| 確認点 | 結果 |
| --- | --- |
| 下書きの作成 | 選んだ商品が下書きとして保存され、`/draft` の件数が処理できた数だけ増える |
| 入力完了の待機と差分チェック | 再出品元の画像5枚に対し下書きも5枚。商品名・価格・説明・各 `select` も入る |
| 完了の検知 | 1件あたり15〜30秒で「完了 n/n」。失敗0件でウォッチドッグにも到達しない |
| 商品間の待機 | 1件目の完了から2件目の再出品ボタンのクリックまで**60秒以上**空く |
| 一覧タブを閉じたとき | 待機中に一覧タブを閉じるとキューが停止し、残りの商品は処理されない |
| 手動で開いた出品フォーム | `data-rbl-form="manual"` になり、ボタンは押されない |

商品間の待機は、下限が60秒であることまでしか確認できない。完了の時刻は Background の
ログにしか無く、Service Worker の console は拡張の外から読めないため、60〜75秒の
どこであったかまでは絞れない。なお待機をまたいで2件目が始まるので、
`chrome.storage.session` からの復元と `chrome.alarms` の経路もあわせて動いている。

### 未検証

**一括削除の動作全体。** DOMの構造と `data-confirm` の挙動までは確認済みだが、
実際に削除を実行しての確認はしていない。**取り消せない操作なので、
ここを変更するなら実機確認までを1単位にすること。**

**説明文の一括置換は 3 件で通しで確認済み（2026-09-28）。** プロトタイプの value setter による
書き込みが React に反映され、「確認する」→「更新する」で保存され、`/sell?is_new=0` への遷移で
完了を検知し、直後の JSON-LD が確定版と一致した（改行は LF のまま。CRLF にはならなかった）。
保存後の編集ページで商品名・価格・画像枚数が変わっていないことも確認した。
最初の実行で完了処理の再入（上記）を見つけて直し、修正後に残り 2 件（NBSP を含む本文）で
2/2 成功を確認した。そのあと残り 120 件を待機 60 秒で流し、120/120 成功
（スキップ・失敗・未確認は 0。約 2 時間）。全 123 件を商品ページの JSON-LD で読み直し、
説明が確定版と一致し、商品名・価格・画像枚数が取得時点から変わっていないことを確認した。

説明欄の本文には **NBSP（U+00A0）が含まれる**商品が多い（出品中 134 件のうち 128 件）。
JSON-LD も編集ページの `textarea` もそのまま保持するので照合には影響しないが、
原本 JSON を別の経路（コピー&ペースト等）で作ると通常の空白に化けて「原本と一致しない」になる。

**注入 UI の作り直し（2026-10-02）の見た目。** ラクマを模したモック上で本物のバンドルを動かして
確認しただけで、ログイン後の実ページには読み込んでいない。ラクマ側の CSS の干渉（`label` や
`input` へのグローバルなスタイルなど）は実ページでしか分からない。

### 調査用のDOMマーカー

Content Script と Service Worker の console ログは拡張の外からは読めないため、
出品フォーム用 Content Script は自分の状態を `<html data-rbl-form="...">` に残す。

| 値 | 意味 |
| --- | --- |
| 無し | Content Script が注入されていない（manifest の matches、または拡張の再読み込み漏れ） |
| `manual` | 注入されたが、自動処理対象ではないと判定した（Background がタブを捕捉できていない） |
| `auto` | 自動処理対象として自動処理（出品・下書き保存・説明文の置換）を実行した |

`manifest.json` を変更したときは、ページのリロードだけでは反映されない。
`chrome://extensions` で拡張自体を再読み込みする必要がある
（`dist/*.js` の変更はページのリロードだけで反映される）。
