# セルフレビュー

目的は**後から直す手戻りを減らすこと**。指摘を増やすことではなく、**あとで確実に踏む穴を潰すこと**を狙う。

## 差分を集める（3 つとも）

レビュー対象は**このブランチが `develop` に入れようとしている変更全体**。直前のコミットだけを見るとブランチ全体を取りこぼす。

```bash
git diff --no-renames develop...HEAD      # このブランチが入れたコミット済みの変更
git diff --no-renames HEAD                # 未コミットの変更（ステージ済み含む）
git ls-files --others --exclude-standard  # 未追跡の新規ファイル
```

- **`...`（3 点）を使う。** `develop..HEAD`（2 点）にすると、`develop` 側が進んでいるときに相手側の変更まで差分に出て、自分が書いていないコードをレビューすることになる。3 点なら**分岐点からこのブランチが入れた変更だけ**。
- **比較元を最新にしてから実行する。** origin があるなら `git fetch origin develop` のあと `git log develop..origin/develop` が空か確かめる。
- **未追跡の新規ファイルは `git diff` に出ない。** 3 つ目を必ず実行する。
- **`--no-renames` を省かない**（移動元のパスが落ちる）。
- **1 本のパイプにまとめない**（どれかが失敗しても全体は成功し、「変更なし」に見えたまま見落とす）。
- **`git status --porcelain` は使わない**（リネームが `R old -> new` の 1 行になりパスとして取り出せない）。

## 観点（この順。当てはまらないものは飛ばす）

### 1. プロダクト方針（最優先）

[CLAUDE.md の「最重要方針」](../../../CLAUDE.md)を弱める変更になっていないか。**触ったパッケージの CLAUDE.md の「最重要方針」と「セルフレビューで見る固有の観点」を開き、そこに列挙された安全装置を 1 つずつ照らす**（[packages/mercari/CLAUDE.md](../../../packages/mercari/CLAUDE.md) / [packages/rakuma/CLAUDE.md](../../../packages/rakuma/CLAUDE.md)）。

- **取り消せない操作のガードが外れていないか。** 一括出品・一括再出品・一括削除・説明文の置換の**対象の絞り込み条件と件数**が変わっていないか。ユーザーが選んでいない商品が対象に入りうるか。確定操作（ボタンのクリック）に至る経路にガードがあるか。
- **サイト側の DOM 変更に耐えるか。** 新しいセレクタをパッケージの定数ファイルの外に直書きしていないか。**要素が見つからないときに黙って続行していないか**（見つからない＝サイト側が変わった可能性なので、安全に止まって知らせる側に倒す）。待機の失敗を呼び出し元に伝えているか。
- **パッケージをまたいで import していないか。** `packages/mercari` ↔ `packages/rakuma` の直接参照は禁止。共有するなら `packages/core`。
- **共有部品（`packages/core`）へ移した変更なら、既存の文字列・キー名・挙動が 1 つも変わっていないか。** ログの接頭辞やストレージのキー名は呼び出し側から注入されているか。

### 2. 壊れても気づけないもの

- **不可逆操作のガード**: 削除・全件置換・一括クリックの**件数と条件**。ループが途中で失敗したとき**部分適用で終わっていないか**（何件目まで処理したかが分かるか）。処理中フラグや `phase` が、例外経路も含めて必ず戻るか。
- **失敗しても止めない処理は、失敗が観測できないと不具合と区別できない。** `catch` で握り潰していないか、logger の `warn` が出るか、失敗が理由付きで積まれるか。**意図的に握り潰す箇所は、その理由がコメントで読めるか。**
- スタブのテストでは検出できない箇所（このリポジトリには自動テストが無いので、**すべてがこれに当たる**。実際に Chrome に読み込んで確認したかどうかを自分に問う）。
- 設定値（セレクタ・待ち時間・ID）をコードに直書きしていないか。パッケージの定数ファイルに置くべきものではないか。

### 3. 実行時に落ちるもの

- 検証なしの型アサーション（`as HTMLElement` など）。DOM から取った要素は `null` になりうる。
- `null` / `undefined` へのアクセス。`querySelector` の戻り値をそのまま使っていないか。
- **`await` 忘れ**。非同期の処理を待たずに次へ進むと、順序が崩れて誤操作につながる。`void` を付けて意図的に待たない箇所は、待たなくてよい理由が読めるか。
- 握り潰した `catch`。
- 後始末されない fire-and-forget（`MutationObserver` の `disconnect`、`setTimeout` / `setInterval` の解除、イベントリスナーの解除、`chrome.alarms`）。
- 外部入力（DOM のテキスト、`chrome.storage` の値、`sendMessage` の応答、fetch した HTML）の未検証。
- secret がログや応答に出ていないか。

### 4. 出す前の形式

- **型チェック・ビルド・lint を実際に通したか**（`npm run check`）。通していないなら通す。**通るのが正常。**
- `npm run format:check` で自分が触ったファイルが増えていないか（メルカリの既存分の失敗は対象外。ラクマは通るのが正常）。
- 一時設定・デバッグ出力・コメントアウトした旧コードが残っていないか。
- 依頼されていない変更が混ざっていないか（既存コードの format 一括修正を含む。**もう片方のパッケージへの「ついで」の同期変更**を含む）。
- **一次資料との食い違いを作っていないか。** 挙動を変えたら、該当パッケージの README（ラクマは設計判断の一次資料）や `docs/ARCHITECTURE.md`（メルカリ）、CLAUDE.md の索引も直す。

## 出し方

- **Must / Should / Nit の 3 段階で最大 5 件**（件数が多いと読まれない）。
  - **Must** = 直さないと先に進めない（壊れている・方針に反する・データを失う）
  - **Should** = 直したほうがよい（いま直さないなら理由が要る）
  - **Nit** = 好みの範囲
- 各指摘は「**どこが・なぜ問題か・どうなると壊れるか**」を 1〜2 行。修正方法の長い説明は要らない。
- **点数を付けない**（較正点が無く再現性がない。平均が重い問題を薄める）。総合評価は Must / Should の件数で書き、合否は「**Must が 0 件か**」で判断する。
- **5 件を埋めようとしない。** 無ければ「Must / Should なし」で終える。

## 指摘しないこと（見つけても書かない。読む量が増えるだけ）

- コードスタイル・フォーマット（ESLint / Prettier の領分）
- 変数名・コメントの有無
- 動作に影響しないリファクタ提案（DRY 化など）。**とくに「2 つのパッケージで似ているから共通化すべき」は書かない**（中身は別実装で、共通化しない方針）
- カバレッジの低さそのもの（**押さえていない挙動を具体的に言えるなら書く**）
- 好みや慣習の違い

## 推測で指摘しない

呼び出し元・呼び出し先まで実際に読んでから書く。**「たぶん壊れる」は書かない。** どう壊れるかを 1 行で言えないなら、指摘ではなく**確認事項**として分ける。
