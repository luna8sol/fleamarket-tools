# 品質チェック

コマンドと現状の正本は [CLAUDE.md の「検証」](../../../CLAUDE.md)。ここには**回し方**を書く。

## 前提: このリポジトリに自動テストは無い

どのパッケージにも `test` スクリプトは無く、テストフレームワークも依存に入っていない。「テストを回す」は**型チェック・ビルド・静的解析を回す**ことを指す。**実行していないテストの結果を報告に書かない。**

## 原則: ルートで全部回す

npm workspaces なので、**リポジトリルートのスクリプトが両パッケージを順に回す。** 合計 1 分弱なので、影響範囲を考える時間のほうが高くつく。絞り込みの判断はしない。

```bash
npm run check           # 型チェック → ビルド → lint を両パッケージ分（通過するのが正常）
npm run format:check    # フォーマット（ラクマは通過が正常。メルカリは既存コードの未通過分だけ落ちる）
```

**すべてリポジトリルートで実行する。** `cd` で移動が必要な場合はサブシェル `(cd dir && ...)` にして持ち越さない。1 パッケージだけ回したいときは `-w` を付ける（例: `npm run typecheck -w packages/rakuma`）。ただし**コミット前は必ず両方回す**（共有設定を触っていなくても、ルートの `node_modules` は共通なので片方だけの確認では足りない）。

## 落ちたときの判断

- **`npm run check` が落ちたら、それは自分の変更のせい。** 直してから再実行する。**通っている状態を壊さないこと。**
  - 出力の `npm error workspace <name>` の行で**どのパッケージで落ちたか**を見る。`--workspaces` は片方が失敗してももう片方を実行してから exit 1 になるので、最後の出力だけ見て判断しない。
- **`npm run format:check` はメルカリ側が元から落ちる**（既存コードに差分。件数は CLAUDE.md の検証表）。落ちたこと自体は異常ではない。**自分が触ったファイルが指摘に増えていないか**で判断する:
  ```bash
  git show HEAD:<path> | npx prettier --stdin-filepath <path> --check
  ```
  増えていれば `npx prettier --write <そのファイル>` で直す。**`npm run format` でリポジトリ全体を一括整形しない**（既存分の差分が本来の変更を埋める）。
- **ラクマ側で `format:check` が落ちたら、それは自分の変更のせい。** 触ったファイルだけ直す。
- **`format:check` が全ファイルで落ちたら、まず改行コードを疑う。** 改行は [.gitattributes](../../../.gitattributes) で LF に固定してある。確認は `git ls-files --eol <パス>` で、`w/` が `lf` かどうか。
- **`npm run build` が通っても、動作確認にはならない。** 自動テストが無いので、挙動を変えたなら Chrome に読み込んで確かめる（`local-setup` スキル）。確かめていないなら**報告に「未検証」と書く**。

## 絞り込む判断をするとき（ドキュメントだけ触った場合など）

絞ってよいのは**ドキュメントだけを触ったとき**に限る。ルートの `package.json` / `package-lock.json` / `tsconfig.base.json` / `eslint.config.js` / `.prettierrc` と、各パッケージの `webpack.config.js` / `tsconfig.json` / `package.json` / `manifest.json` は全体に効くので、触ったら**回す側**に入れる。

変更パスは**この 3 つとも**集める:

```bash
git diff --name-only --no-renames develop...HEAD      # このブランチが入れたコミット済みの変更
git diff --name-only --no-renames HEAD                # 未コミットの変更（ステージ済み含む）
git ls-files --others --exclude-standard              # 未追跡の新規ファイル
```

- **`...`（3 点）を使う。** `develop..HEAD`（2 点）にすると、`develop` 側が進んでいるときに相手側の変更まで差分に出る。3 点なら**分岐点からこのブランチが入れた変更だけ**になる。
- **比較元を最新にしてから実行する。** origin があるなら `git fetch origin develop` のあと `git log develop..origin/develop` が空か確かめる。空でなければ先に `git switch develop && git pull --ff-only` で追いつかせる。
- **`--no-renames` を省かない。** 既定ではリネームが畳まれて移動後のパスしか出ず、移動元のディレクトリを対象から落とす。
- **`| sort -u` のような 1 本のパイプにまとめない。** どれかが失敗してもパイプ全体は成功し、「変更なし」に見えたまま未検証で進む。3 回別々に実行して、それぞれの結果を見る。
- **`git status --porcelain` は使わない。** リネームが `R old -> new` の 1 行になりパスとして取り出せない。

## CI

CI は存在しない（`.github/workflows/` 無し）。CI を追加・変更したら、**そのワークフローが実行するコマンドを手元でも 1 度通す**。

## 結果の報告

- **失敗したままコミットしない。** 直してから再実行する（元から落ちているメルカリの `format:check` を除く）。
- **実行したコマンドと結果を控えて、報告にそのまま書く。** パッケージごとに書く。

```
npm run check          → 通過（mercari / rakuma とも）
npm run format:check   → mercari: <N> ファイルに差分（すべて既存コード。今回の変更分は 0） / rakuma: 通過
テスト                 → 未実行（このリポジトリにテストは存在しない）
Chrome での動作確認    → 未実施
```

- **実行していないコマンドの結果を書かない。未検証の項目は未検証と明記する**（書かない方が減点）。
