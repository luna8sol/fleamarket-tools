# タスクに着手する

規約の正本は [CLAUDE.md](../../../CLAUDE.md)。ここには**手順**だけを書く。

## 1. 読む（推測で書き始めない）

- **CLAUDE.md の「着手前に読むもの」索引にある一次資料と、該当コードを直接読む。** 索引に無い領域なら、該当ディレクトリのコードを読んでから始める。
- **文書とコードが食い違ったらコードが正。** 既知のズレは CLAUDE.md の「既知の状態」にまとめてある。古い記述を見つけたらその場で直す。
- **索引は `develop` 時点の構成を指している。** 未統合の作業ブランチの上にいると構成が違うことがあるので、**どのブランチの上で作業しているかを確認してから**ファイルを開く。
- **確かめていないことを断定しない。** ラクマ側の DOM・Chrome 拡張 API の制約は、実際に動かすか公式ドキュメントで確認するまで「要検証」と明記する。「たぶん動く」で設計を進めない。

## 2. スコープを決める

- **依頼されたスコープを勝手に広げない。** 作業中に見つけた別の問題は、直さずに書き出して報告する。**1 コミットは 1 つの目的に絞る。**
  - **既存コードの一括整形を混ぜない。** `npm run format` でリポジトリ全体を整形すると、差分が膨れて本来の変更が埋もれる。触ったファイルだけ直す。
- **方針決めと実装を 1 つの作業単位に混ぜない。** 方針が定まっていないものは、**決めて書き残すまでを 1 単位**にし、実装は別にする。決まっていない状態で書いた実装は、方針が動いたときにまるごと捨てることになる。
- **方針を変える判断をしたら理由を残す。** 選ばなかった案とその理由まで書く。

## 3. ブランチを切る

`develop` が統合ブランチ。**`develop` と `main` で直接作業しない。**

```bash
git switch develop
git switch -c <feature|fix|docs|refactor>/<英小文字の短い説明>
```

`develop` は origin に無いローカルブランチなので `git pull` は不要（origin に push した後は `git pull --ff-only` を先に実行し、失敗したら**勝手にマージせず報告して指示を仰ぐ**）。

命名規約は [CLAUDE.md](../../../CLAUDE.md) の「ブランチ運用の補足」にある（`feature/` を既定にせず、中身で選ぶ）。

**worktree で作業しているときは、そのブランチは既に切られている。** 新しく切らず、名前が規約どおりか確認する。自動命名（`claude/...`、`worktree-...`）のままなら直す:

```bash
git branch --show-current
git branch -m <規約名>
```

## 4. 実装する

CLAUDE.md の「最重要方針」に照らしながら書く。とくにこのリポジトリでは:

- 一括出品・一括再出品は**取り消せない実操作**。対象の絞り込み条件と件数のガードを先に決める。
- 編集ページで自動クリックする経路を触るなら、**`CHECK_AUTO_TAB` の確認を必ず通す**（手動で開いたページで動かさない）。
- セレクタとページ判定は**ラクマ側の変更で壊れる**。一覧ページの新しいセレクタは `src/content/list/infra/constants.ts` に置き、要素が見つからないときに黙って続行しないこと。編集ページのボタンは `css-*` クラスではなくテキストで探す。

## 5. 既定の停止点はコミット

1. **品質チェックを通す** → `quality-check` スキル
2. **セルフレビューする** → `self-review` スキル
3. **コミットする** → `commit` スキル
4. **やったことを数行で報告して終える**

コミットまでで止める。**マージまで自動で進めない。** 統合するかどうかは人が判断する。「マージして」と言われたときだけ `merge` スキルに進む。作業ブランチの push もしない（ローカル限りの運用）。

**逆方向の指示を尊重する。** 「コミットしないで」「品質チェックだけ」「調べるだけ」と言われたら、そこで止めて残りをやらない。
