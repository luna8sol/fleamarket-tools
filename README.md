# Rakuma Bulk Lister

ラクマ（fril.jp）の出品作業を一括化する Chrome 拡張機能。

- **一括下書き保存**: 「出品した商品」（`/sell`）で商品を選択し、フリマアシストの再出品ボタンを順にクリックして、複製された内容を**下書きとして保存**する
- **下書き一括出品**: 「下書きの商品」（`/draft`）で下書きを選択し、順に出品する
- **一括削除**: `/sell`・`/draft` のどちらでも、選択した商品を順に削除する

再出品はこの2段構えで行う。`/sell` で下書きに溜めてから、内容を確認して `/draft` で公開する。
`/sell` 側の操作では出品は発生しない。

## 前提

- 一括再出品には Chrome 拡張機能「フリマアシスト」のインストールが必要（`/sell` に注入される `#clone-item` ボタンを利用するため）
- 下書き一括出品はフリマアシスト不要

## 仕組み

```
① 一覧ページ (content-list.js)
   /sell:  チェックボックスで選択 → フリマアシストの再出品ボタンをクリック
   /draft: チェックボックスで選択 → Background が編集ページをタブで開く

   削除: チェックボックスで選択 → 削除リンクをクリック（ページ遷移が起きる）

② Background (background.js)
   処理キューの管理・タブの追跡・完了の検知・商品間の待機時間制御

③ 出品フォーム (content-form.js)
   Background に自動処理対象タブか確認したうえで、モード別にボタンを押す
   relist  /item/new           （フリマアシストが開く）→「下書きに保存する」
   publish /drafts/{hash}/edit （Background が開く）  →「確認する」→「出品する」
```

### 出品完了の判定は Background 側で行う

出品フォームのタブを `chrome.tabs.onUpdated` で監視し、**ボタンを押したあとに
出品フォームの URL から離れたこと**をもって完了とみなす。

Content Script 側で遷移を監視しない理由は、遷移先が別オリジン（`item.fril.jp`）に
なりうるため。その場合 Content Script は遷移前に破棄され、完了を見届けられない。

Background が離脱を見始めるのは `FORM_SUBMITTED` を受け取ってからなので、
Content Script は**ボタンを押す前に**これを送る（押した直後だと、遷移で
破棄されて送れないことがある）。**送れたことを確認できなければ押さない。**
押したのに Background が知らないままだと、遷移しても完了とみなされず、
ウォッチドッグが時間切れになるまで「自動操作が始まりませんでした」としか
分からない。送れなかった場合は通信失敗を理由に失敗として扱う。

### 入力が終わるまで待ってから保存する

フリマアシストの流し込みはテキストが速く、**画像だけ遅い**
（`img.fril.jp/tmp_img/` へアップロードされるまで時間がかかる）。
「何か値が入ったか」で判断すると早すぎて、画像が欠けた下書きができる。

待ち方は、再出品元の内容が分かっているかで変える。

- **分かっている場合**: 各項目のスナップショット（商品名・価格・説明・各 `select`・
  画像枚数）が**元と一致するまで**待つ。
- **分からない場合**: スナップショットが**5秒間まったく変化しなくなるまで**待つ。

どちらも0.5秒ごとに確認し、最大2分待つ。

「変化が止まったか」だけで判断してはいけない。画像は1枚ずつ間隔を空けて
アップロードされるため、アップロードの合間が安定時間を超えると、
**画像が足りないまま完了と誤判定**して欠けた下書きができてしまう。

カテゴリや配送方法はボタンのラベルとして出るが、手数料の案内など内容が
変わりうるボタンも混ざるため、安定判定には含めない。

### 再出品元との差分チェック

保存の直前に、再出品元の商品ページ (`https://item.fril.jp/{hash}`) の内容と
突き合わせる。**足りていない場合は保存せず、差分を失敗理由として残す。**

検出したいのは**内容の欠落**なので、比較には向きを持たせる。フォーム側が元より
多い・書式が違うぶんは問題にしない。JSON-LD とフォームは別々のシリアライズ経路で、
同じ内容でも数文字ずれることが実際にある（実測: 元779文字に対しフォーム782文字）。
厳密一致を求めると、内容は揃っているのに永久に保存できなくなる。

| 項目 | 判定 |
| --- | --- |
| 商品名 | 空白を落とした状態で不一致なら失敗 |
| 商品説明 | フォーム側が5文字以上**短ければ**失敗（長いぶんは可） |
| 価格 | 数値として不一致なら失敗 |
| 画像枚数 | フォーム側が**少なければ**失敗（多いぶんは可） |

商品ページはサーバーレンダリングされており、JSON-LD (Product) から
商品名・説明・価格・ブランドが取れる。画像は JSON-LD に1枚しか無いため、
og:image と同じ商品番号を持つ大サイズ (`/l/`) の画像URLを重複を除いて数える。

実機で、JSON-LD とフォームの値は商品名・説明とも完全一致することを確認済み
（ハッシュ一致）。そのため文字列は厳密に比較する。

取得は Background で行う（`item.fril.jp` は別オリジンのため host_permissions が必要）。
Service Worker には DOMParser が無いので正規表現で抜き出す。
取得に失敗した場合は差分チェックを省略し、入力が落ち着いたかどうかだけで判断する。

### 一括削除はページ遷移をまたいで進む

ラクマの削除は `jquery_ujs` のリンク（`data-method="delete"`）で、`data-remote` を
持たないため**クリックするとページ遷移が起きる**。1件削除するたびに一覧が
再読み込みされ、Content Script も作り直される。そのため削除もキューで駆動する。

```
Background → CLICK_DELETE → 一覧で削除リンクをクリック → ページ遷移
  → 一覧が再描画 → Content Script が LIST_READY（表示中の商品ID）を送る
  → Background が対象IDの消滅を確認 → 成功として次へ
```

#### 削除すると1ページ目に戻る

削除後の再読み込みで一覧は**1ページ目に戻る**。そのため2ページ目以降の商品を続けて
削除しようとすると、対象がDOM上に無くて失敗する。

対策として、**開始時のページ番号を覚えておき、削除のたびにそのページへ戻してから**
対象を探す。次の2つが成り立つので、そのページに戻れば必ず見つかる。

- **対象は必ず1ページに収まる**。`syncItems` がDOM変化のたびに
  `SelectionManager.retain()` を呼ぶため、ページを送った時点で前ページの選択は
  破棄される。つまり開始時の選択は現在ページのものだけになる。
- **同じページの商品を削除しても、そのページの残りは逃げない**。削除すると後続が
  1つずつ前に詰まるが、ページP内の商品はP内に留まり、P+1以降の商品がPへ
  繰り上がってくるだけ。Pより前の商品は動かない。

ページ送りはURLを変えずAJAXで一覧を差し替えるので、`.pagination .page.current` の
表示が目的のページ番号に変わるまで待つ。「最後のページ」へのリンクはラベルが記号で
番号を持たないため、リンクの解決はテキストと `href` の両方で行う。これにより
1ページ目から5ページ目へも1回の移動で到達できる。「…」で省略されていて直接の
リンクが無い場合は、目的地に近づく方向へ段階的に移動する。

想定が崩れて目的のページに見つからなかった場合の保険として、全ページを順に探す。

#### 成否の判定

「表示中の一覧に対象が残っていないこと」は削除の証拠にならない。1ページ目に戻るので、
別ページにいるだけかもしれないため。

- 件数が読めるページ（`/sell`）: **総件数が減ったか**で判定する。
  情報行（`122件中 31 - 60件`）はタブごとに存在するので、表示中のものだけを使う。
- 件数が読めないページ（`/draft` はページャが無く全件表示）:
  対象IDが一覧に残っていないかで判定する。

押した結果を確認してから次へ進むので、削除できていないのに進み続けることがない。

商品間の待機は Content Script 側で 2〜4 秒入れる。`chrome.alarms` は短い遅延を
指定できず、また削除はページ遷移そのものが間隔になるため、他モードのような
60〜75 秒の待機は挟まない。

### 削除の確認ダイアログの扱い

削除リンクには `data-confirm="本当に削除してもよろしいですか？"` が付いており、
`jquery_ujs` がネイティブの `confirm()` を出す。これは Content Script 側から
応答できず処理が止まるため、**クリックの直前だけ `data-confirm` を外し、直後に必ず戻す**。

そのぶん、一括削除の開始前に拡張側で必ず確認を取る（件数と取り消せない旨を表示）。
手動でクリックしたときの確認ダイアログはそのまま残る。

削除リンクは `data-method="delete"` で特定したうえで、**ラベルが「削除」であることも
確認**してからクリックする。取り消せない操作なので、どちらか一方でも合わなければ
クリックせず失敗として記録する。

### Service Worker の破棄に耐える

MV3 の Service Worker はアイドル状態が続くと破棄される。本拡張は商品間に 60〜75 秒の待機を
挟むため、待機中の破棄は**必ず起きる**。そのためキューの状態は変更のたびに
`chrome.storage.session` へ書き戻し、すべてのイベントハンドラの先頭で復元してから処理する。

タイマー類も `setTimeout` ではなく `chrome.alarms` を使う（`setTimeout` は Service Worker の
破棄とともに消えるため）。

- `next-item` アラーム: 次の商品の処理開始
- `watchdog` アラーム: 1 商品の処理が 5 分以内に完了しない場合に打ち切る（`ITEM_WATCHDOG_MS`）

### 一覧の描画をMutationObserverで待つ

商品リストはサーバーHTMLに含まれず、クライアント側で描画される。さらにページ送りは
URLを変えずにAJAXで一覧を差し替えるため、Content Script は再実行されない。
そのため `MutationObserver` で `body` 配下の変化を監視し、商品が現れるたびに
チェックボックスを付け直す（付与済みの商品はスキップするので何度呼んでも安全）。

一覧から消えた商品の選択は破棄する。ページ送りで表示外になった商品を選択したまま
開始してしまうのを防ぐため。

### その他の設計上の判断

- 出品フォームのボタンは Chakra UI のハッシュクラスのため**テキストで特定**する
- 手動で開いた出品ページでは何もしない（Background への確認で判別）
- ボタンを押す前にフォームへ値が入るのを待つ（フリマアシストの入力完了前に
  空のフォームを保存・送信しないため）
- 押すボタンはページのボタン名ではなくモードで決める。`/item/new` と
  `/drafts/{hash}/edit` はどちらも「下書きに保存する」と「確認する」を持つため
- 失敗時（バリデーションエラー・タイムアウト等）はタブを残してユーザーが確認できるようにする
- 一覧ページを再読込しても、実行中のキューの進捗は Background から取得して復元される

### 実機で確認済みの動作（2026-09-20 時点）

**publish モード（`/draft` の一括出品）は通しで動く。** 下書き1件を選んで実行し、
次を確認した。

| 確認点 | 結果 |
| --- | --- |
| 出品の実行 | 選んだ下書きが実際に出品された。`/draft` から消え、`/sell`（出品した商品）に現れる |
| 完了の検知 | 実行から20秒以内に「完了 1/1」。失敗0件でウォッチドッグにも到達しない |
| 「出品する」押下後の遷移 | **URLが変わる。** Background の URL 監視による完了判定がそのまま機能する |

懸念していた「出品完了でURLが変わらず、実際には出品されているのにウォッチドッグで
失敗扱いになる」ケースには該当しなかった。Content Script 側からの完了通知を足す必要はない。

### 未検証

**一括削除の動作全体。** DOMの構造と `data-confirm` の挙動までは確認済みだが、
実際に削除を実行しての確認はしていない。**取り消せない操作なので、
ここを変更するなら実機確認までを1単位にすること。**

### 調査用のDOMマーカー

Content Script と Service Worker の console ログは拡張の外からは読めないため、
出品フォーム用 Content Script は自分の状態を `<html data-rbl-form="...">` に残す。

| 値 | 意味 |
| --- | --- |
| 無し | Content Script が注入されていない（manifest の matches、または拡張の再読み込み漏れ） |
| `manual` | 注入されたが、自動処理対象ではないと判定した（Background がタブを捕捉できていない） |
| `auto` | 自動処理対象として自動出品を実行した |

`manifest.json` を変更したときは、ページのリロードだけでは反映されない。
`chrome://extensions` で拡張自体を再読み込みする必要がある
（`dist/*.js` の変更はページのリロードだけで反映される）。

## コマンド

```bash
npm run build          # webpack でビルド（開発用）
npm run build:prod     # 本番用ビルド
npm run lint           # ESLint
npm run format         # Prettier
npm run clean          # dist を削除
```

## ディレクトリ構造

```
src/
├── background/    # 処理キュー・タブ追跡・完了検知（Service Worker）
├── common/        # Background ⇔ Content 共有（メッセージ型定義・URL判定・logger）
├── content/
│   ├── list/      # 一覧ページ用（infra / logic / ui の3層）
│   └── form/      # 出品フォーム用（/drafts/{hash}/edit と /item/new の自動出品）
└── popup/
```

## インストール（開発版）

1. `npm install && npm run build`
2. Chrome の `chrome://extensions` で「パッケージ化されていない拡張機能を読み込む」からこのディレクトリを選択
